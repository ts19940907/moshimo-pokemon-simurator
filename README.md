# moshimo-pokemon-simurator

もしもポケモンシミュレーターのリポジトリです。初代シングルの対戦シミュレーターを、まずはブラウザ（Expo Web）で動かします。

## 開発

```bash
npm install
npm run web
```

タイトル画面の「スタート」からメニューへ進み、世代（対戦ルール・使えるポケモン・使える技）と禁止制限・対戦相手・情報公開を選んで編成へ進みます。いまは初代のみ選択できます。編成では図鑑順に1ページ10体ずつ表示し、6体を選びます。選出画面はこれから用意します。

ポケモンマスターは Supabase の **`moshimo` スキーマ**（`pokemon` / `abilities`）で管理します。テーブル定義は `supabase/migrations/` 、初代シードは `supabase/seed/` です。編成画面はこのテーブルから取得します（`.env` に URL / anon key が必要）。

## Git ルール

ローカルでの git 操作は [`.claude/skills/git-rules/SKILL.md`](.claude/skills/git-rules/SKILL.md) に従います。  
エージェントに「コミットして」「プッシュして」「ブランチを作って」と依頼したときも、このスキルを参照します。

### 絶対ルール

- **main ブランチへローカル環境でコミットしない。** 作業前に現在ブランチを確認し、`main` 上ならコミットを拒否して分岐を促す
- **dev は main から派生して作る。** `dev` が無ければ `main` から作成する。作業用ブランチは必ず `dev` から派生する
- **1問ずつ聞く。** まとめて質問しない。選択肢がある確認は選べる形で提示する

### ブランチ戦略

```
main
 └── dev
      ├── feature/<ブランチ名>
      └── fix/<ブランチ名>
```

### ブランチ作成フロー

1. `dev` の有無を確認する。無ければ `main` から `dev` を作成する
2. **機能追加かソース修正のどちらかを聞く**
3. どちらか聞いた上で、**ブランチ名を入力してもらう**
4. 選択に応じて `dev` から派生してブランチを作成する
   - 機能追加 → `feature/[入力したブランチ名]`
   - 修正 → `fix/[入力したブランチ名]`

### コミットフロー

1. 現在ブランチを確認する。`main` ならコミットしない
2. 作業用ブランチ（`feature/*` または `fix/*`）上であることを確認する。違えばブランチ作成フローへ誘導する
3. コミット前に次を確認する
   - **自分でコミットメッセージを入力したいか**
   - **修正内容に相応しいメッセージを考えてもらいたいか**
4. 前者ならユーザーのメッセージでコミットする。後者なら差分を見て提案し、承認後にコミットする

### プッシュフロー

1. 現在ブランチを確認する（`feature/*` または `fix/*` を想定）
2. 作業ブランチにプッシュする
3. 作業ブランチにプッシュ後 **リモートのdev ブランチにマージして問題ないか** を確認する
4. 問題ない場合のみ、確認した方針どおりにマージを進める
5. 問題がある・まだ早い場合は、マージせず作業ブランチの扱いについて次の指示を待つ

### やってはいけないこと

- `main` へのローカルコミット
- 確認なしのブランチ作成・コミットメッセージ決定・dev へのマージ／プッシュ
- `main` や `dev` 以外から直接 `feature/*` / `fix/*` を切ること（必ず `dev` から）
