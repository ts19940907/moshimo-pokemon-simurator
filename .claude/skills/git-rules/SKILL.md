# Git Rules

ローカルでの git 操作はこのスキルのルールに従う。ルールを飛ばして実行しない。

## 絶対ルール

- **main ブランチへローカル環境でコミットしない。** 作業前に現在ブランチを確認し、`main` 上ならコミットを拒否して分岐を促す
- **`release` へ直接コミットしない。** `release` は Vercel にデプロイするためのブランチ。デプロイするソース（`dev3` または `dev4`）をマージして使う
- **`dev`・`dev2` ブランチは使わない。** 新規作業・マージの対象にしない（過去ブランチとして扱い、作業基点にしない）
- **世代ブランチ（`dev3` / `dev4`）上で変更作業を始めない。** ファイル変更がかかる操作を指示されたとき、現在ブランチが `dev3`・`dev4` などの世代ブランチなら、そのまま進めず **作業用ブランチを作り直す（新規作成する）必要があるか** を確認する。必要ならブランチ作成フローへ進む
- **作業用ブランチは、作業対象の世代ブランチから派生する。** リリース済みシステムの改修なら `dev3`、新規機能追加なら `dev4`
- **1問ずつ聞く。** まとめて質問しない。選択肢がある確認は選べる形で提示する

## ブランチ戦略

```
release                 # Vercel デプロイ用
 ├── dev3               # リリース済みシステムの改修用
 │    ├── feature/<ブランチ名>
 │    └── fix/<ブランチ名>
 └── dev4               # 新規機能追加用（release から派生）
      ├── feature/<ブランチ名>
      └── fix/<ブランチ名>
```

- **`release` は Vercel にデプロイするためのブランチ**
- **`dev3` はリリース済みシステムの改修用ブランチ**（本番相当の改修・バグ修正など）
- **`dev4` は新規機能追加用ブランチ**（`release` から派生）
- **`dev`・`dev2` はもう使わない**（作業基点・マージ先にしない）
- 新しい世代ブランチが必要なら `release` から派生して作る（例: `dev5`）

## ブランチ名・コミットメッセージの指摘

ブランチ名やコミットメッセージをユーザーが指定したとき、作成・コミットの実行前に内容を点検する。問題があれば指摘し、修正案を出してから進める（勝手に直して実行しない）。

- **スペルミス・誤字脱字**を見つけたら指摘する（英語の綴り、ローマ字、日本語の誤字、ハイフン位置の明らかな誤りなど）
- **コミットメッセージ**について、差分の内容によりふさわしい表現が思いついたら指摘・提案する（例: 実際は修正なのに「追加」になっている、範囲が広すぎる／狭すぎる、事実とずれる）
- 指摘するときは、問題点・理由・修正案を短く示し、**元の案のまま進めるか／修正案にするか**を確認する
- 問題がなければ指摘せず、そのままフローを進める

## ブランチ作成フロー

1. 作業対象を確認する（リリース済み改修 → `dev3`、新規機能追加 → `dev4`）
2. 対象の世代ブランチの有無を確認する。無ければ `release` から作成する
3. **機能追加かソース修正のどちらかを聞く**
4. どちらか聞いた上で、**ブランチ名を入力してもらう**
5. 入力されたブランチ名にスペルミス・誤字脱字があれば指摘し、修正の有無を確認する
6. 選択に応じて、対象の世代ブランチ（`dev3` または `dev4`）から派生してブランチを作成する
   - 機能追加 → `feature/[入力したブランチ名]`
   - 修正 → `fix/[入力したブランチ名]`

### 短縮指定（bc）

`bc:[ブランチ名],[種類],[派生元のブランチ名]` で指示されたら、ブランチ作成フローの質問（作業対象・機能追加か修正か・ブランチ名）を省いてブランチを作成する。

- 種類: `fi` → `fix/[ブランチ名]`、`fe` → `feature/[ブランチ名]`
- 例: `bc:select-pokemon-form,fi,dev3` → `dev3` から `fix/select-pokemon-form` を作成
- 作成前に派生元を最新にする（`git checkout [派生元]` → `git pull origin [派生元]`）
- ブランチ名にスペルミス・誤字脱字があれば、作成前に指摘して修正の有無を確認する。問題がなければ質問せずに作成する
- 派生元が `dev3`・`dev4` 以外（`release`・`main`・`dev`・`dev2` など）のときは、本当にそのブランチから作るか確認し、了承があれば作成する
- 種類が `fi`・`fe` 以外のとき、または同名のブランチが既にあるときは、作成せずに指定し直してもらう

### 短縮指定（rb）

`rb:[変更前のブランチ名],[変更後のブランチ名]` で指示されたら、ブランチ名を変更する。

- ブランチ名は `feature/`・`fix/` を付けずに書き、変更前の接頭辞をそのまま引き継ぐ
- 例: `rb:fourth-simulator-screen,fourth-third-generation` → `feature/fourth-simulator-screen` を `feature/fourth-third-generation` に変更
- 変更前の名前に一致するブランチがないときは、近い名前のブランチ（今いるブランチなど）を示して、それを変更するか確認する
- 変更後の名前にスペルミス・誤字脱字があれば、変更前に指摘して修正の有無を確認する。同名のブランチが既にあるときは、変更せずに指定し直してもらう
- 変更前のブランチがリモートにあるときは、リモートも新しい名前でプッシュして古い名前を削除するか確認する

### 短縮指定（cb）

`cb:[ブランチ名]` で指示されたら、そのブランチに切り替える。

- 例: `cb:dev3` → `dev3` に切り替え、`cb:fourth-third-generation` → `feature/fourth-third-generation` に切り替え
- ブランチ名は `feature/`・`fix/` を付けずに書いてもよい。完全に一致するブランチがなければ `feature/[ブランチ名]`・`fix/[ブランチ名]` を探す。候補が複数あるとき、または見つからないときは、近い名前のブランチを示して確認する
- ローカルになくリモートにだけあるときは、リモートを追跡するローカルブランチを作って切り替える
- 未コミットの変更があるときは切り替えず、コミット・スタッシュ・そのまま持っていくのどれにするか確認する
- 切り替え後、リモートにあるブランチなら `git pull origin [ブランチ名]` で最新にする
- 切り替え先が `dev3`・`dev4`・`release` のときは、そのブランチ上でファイル変更を始めないこと（絶対ルール）を守る

## コミットフロー

1. 現在ブランチを確認する。`main` または `release` ならコミットしない
2. 作業用ブランチ（`feature/*` または `fix/*`）上であることを確認する。違えばブランチ作成フローへ誘導する
3. コミット前に次を確認する
   - **自分でコミットメッセージを入力したいか**
   - **修正内容に相応しいメッセージを考えてもらいたいか**
4. 前者なら、ユーザーのメッセージを点検する
   - スペルミス・誤字脱字があれば指摘する
   - 差分によりふさわしいメッセージが思いついたら指摘・提案する
   - 指摘した場合は、元のままか修正案かを確認してからコミットする
5. 後者なら差分を見て提案し、承認後にコミットする

## プッシュフロー

1. 現在ブランチを確認する（`feature/*` または `fix/*` を想定）
2. 作業ブランチにプッシュする
3. 作業ブランチにプッシュ後、**作業対象の世代ブランチ（`dev3` または `dev4`）へリモートマージして問題ないか** を確認する
4. 問題ない場合のみ、確認した方針どおりにマージを進める
5. 問題がある・まだ早い場合は、マージせず作業ブランチの扱いについて次の指示を待つ
6. **リモートの世代ブランチへのマージが完了したら、ローカルもその世代ブランチに切り替える**（例: `git checkout dev4` → `git pull origin dev4`）。作業ブランチに残したままにしない
7. **`release` へのマージはデプロイするときだけ。** 作業ブランチのマージ後に勝手に `release` へ入れない。ユーザーがデプロイ用マージを指示したときだけ、対象世代ブランチを `release` へマージしてプッシュする

### 短縮指定（cm）

`cm:[コミットメッセージ],[操作],[マージ先のブランチ名]` で指示されたら、コミットフロー・プッシュフローの質問（メッセージを自分で入力するか・世代ブランチへマージしてよいか）を省いて、指定された操作を行う。

- 操作はカンマ区切りで、必要なものだけを書く: `c` → コミット、`p` → プッシュ、`m` → マージ（コミットの結合 `c[数字]`・`cc` と、リベースの `r` は後述）
- 例: `cm:フォルム違いのポケモンを選択できるよう修正,c,p,m,dev3` → コミット・プッシュして `dev3` へマージ
- 例: `cm:ゆびをふるの修正,c` → コミットだけ
- 読み取り方: 末尾から見て、操作（`c`・`c[数字]`・`cc`・`p`・`m`）以外の最後の項目がマージ先、操作の並びが操作、残りがコミットメッセージ
- 書かれた順に関係なく、コミット → プッシュ → マージの順に行う
- 操作が1つも書かれていないときは、どの操作を行うか確認する
- コミット前の現在ブランチの確認（コミットフローの 1・2）は省かない
- コミットメッセージにスペルミス・誤字脱字があるとき、または差分によりふさわしい表現があるときは、コミット前に指摘して元のままか修正案かを確認する。問題がなければ質問せずに進める
- `m` があるのにマージ先が書かれていないときは、マージ先を確認する
- マージ先が `dev3`・`dev4` 以外（`release`・`main`・`dev`・`dev2` など）のときは、本当にそのブランチへマージするか確認し、了承があればマージする
- マージ後は、プッシュフローの 6 と同じくローカルをマージ先のブランチに切り替えて最新にする

#### コミットの結合（c[数字]・cc）

- `c` の後に数字があるとき（`c1`・`c2` …）は、コミットしたうえで、直前の [数字] 個のコミットと結合して1つのコミットにする
  - 例: `cm:リベースとブランチ名変更の独自コマンドを追加,c1` → 今回の変更を直前の1コミットにまとめる
  - 未コミットの変更がないときは新しいコミットを作らず、最新のコミットと、その前の [数字] 個のコミットを結合する
- `cc` のときは、`c` が書かれていなくてもコミットし、直近の履歴（`git log --oneline`）を表示して、どこまでを1つに結合するか確認してから結合する
- 結合したコミットのメッセージは `cm` で指定したメッセージにする（点検はコミットと同じ）。結合する内容とメッセージが合わないときは修正案を出す
- 結合は `git reset --soft` で戻してからコミットし直す
- 結合する範囲に、世代ブランチ（`dev3`・`dev4`）や `release` に入っているコミット、またはマージコミットが含まれるときは結合せず、範囲を指定し直してもらう
- 結合する範囲にプッシュ済みのコミットが含まれるときは、強制プッシュ（`--force-with-lease`）が必要になることを伝え、了承があれば進める

#### リベース（r）

`cm:r,[土台のブランチ名],[付け直すブランチ名]` で指示されたら、付け直すブランチを土台のブランチの上にリベースし、リモートへ強制プッシュする。`r` はコミットメッセージを取らず、`c`・`p`・`m` と組み合わせない。

- 例: `cm:r,release,dev4` → `dev4` を `release` の上に付け直し、リモートの `dev4` を上書きする
- 手順
  1. 作業ツリーに未コミットの変更がないことを確認する
  2. 付け直すブランチをリモートと同じ状態にし、リベース前のコミット ID を控える
  3. リベース前の状態を `backup/[付け直すブランチ名]-before-rebase`（既にあれば末尾に `-2`・`-3` …）として残す
  4. `git rebase origin/[土台のブランチ名]` を実行する。競合したら、両方の変更を生かす形で解消し、どう解消したかを報告する
  5. リベース前後の差分（`git diff --stat backup/... [付け直すブランチ名]`）が土台側の変更だけであることを確かめ、テストと型チェックを流す
  6. `git push --force-with-lease=[付け直すブランチ名]:[控えたコミット ID] origin [付け直すブランチ名]` でプッシュする
  7. 付け直したブランチから派生した作業ブランチが古い履歴のまま残る場合は、そのことを報告する
- 付け直すブランチが `release`・`main` のときは、本当に履歴を書き換えるか確認し、了承があれば進める

## やってはいけないこと

- `main` へのローカルコミット
- `release` への直接コミット、および確認なしの `release` へのマージ／プッシュ
- **`dev`・`dev2` を作業基点・マージ先にすること**（もう使わない）
- 確認なしのブランチ作成・コミットメッセージ決定・世代ブランチ（`dev3` / `dev4`）へのマージ／プッシュ
- スペルミスやよりふさわしいコミットメッセージの指摘をせずに、そのままブランチ作成・コミットを進めること
- `main`・`release`・別世代のブランチから、作業対象でない世代へ `feature/*` / `fix/*` を切ること（必ず作業対象の `dev3` または `dev4` から）
- リモートの世代ブランチへのマージ完了後に、ローカルをその世代ブランチへ戻さず作業ブランチに居続けること
- ローカルが `dev3` / `dev4` / `release` の状態で、確認なしにファイル変更を始めること
