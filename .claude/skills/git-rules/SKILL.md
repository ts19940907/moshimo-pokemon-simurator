# Git Rules

ローカルでの git 操作はこのスキルのルールに従う。ルールを飛ばして実行しない。

## 絶対ルール

- **main ブランチへローカル環境でコミットしない。** 作業前に現在ブランチを確認し、`main` 上ならコミットを拒否して分岐を促す
- **`release` へ直接コミットしない。** `release` は Vercel にデプロイするためのブランチ。デプロイする世代のソース（`dev` または `devN`）をマージして使う
- **世代ブランチ（`dev` / `devN`）上で変更作業を始めない。** ファイル変更がかかる操作を指示されたとき、現在ブランチが `dev`・`dev2` などの世代ブランチなら、そのまま進めず **作業用ブランチを作り直す（新規作成する）必要があるか** を確認する。必要ならブランチ作成フローへ進む
- **作業用ブランチは、作業対象の世代ブランチから派生する。** 第1世代なら `dev`、第2世代なら `dev2`、第N世代なら `devN`
- **1問ずつ聞く。** まとめて質問しない。選択肢がある確認は選べる形で提示する

## ブランチ戦略

```
release                 # Vercel デプロイ用
 ├── dev                # 第1世代のソース管理
 │    ├── feature/<ブランチ名>
 │    └── fix/<ブランチ名>
 ├── dev2               # 第2世代のソース管理（release から派生）
 │    ├── feature/<ブランチ名>
 │    └── fix/<ブランチ名>
 └── devN               # 第N世代のソース管理（dev の後ろに世代番号）
      ├── feature/<ブランチ名>
      └── fix/<ブランチ名>
```

- **`dev` は初代を管理するブランチ**
- **`release` は Vercel にデプロイするためのブランチ**
- **2世代以降は `dev2` のように、`dev` の後ろに世代の数字がついたブランチでソースを管理する**（第3世代なら `dev3`）
- 第2世代以降の世代ブランチ（`dev2` など）は `release` から派生して作る
- `dev` が無ければ `main` から作成する（初代のみ）

## ブランチ名・コミットメッセージの指摘

ブランチ名やコミットメッセージをユーザーが指定したとき、作成・コミットの実行前に内容を点検する。問題があれば指摘し、修正案を出してから進める（勝手に直して実行しない）。

- **スペルミス・誤字脱字**を見つけたら指摘する（英語の綴り、ローマ字、日本語の誤字、ハイフン位置の明らかな誤りなど）
- **コミットメッセージ**について、差分の内容によりふさわしい表現が思いついたら指摘・提案する（例: 実際は修正なのに「追加」になっている、範囲が広すぎる／狭すぎる、事実とずれる）
- 指摘するときは、問題点・理由・修正案を短く示し、**元の案のまま進めるか／修正案にするか**を確認する
- 問題がなければ指摘せず、そのままフローを進める

## ブランチ作成フロー

1. 作業対象の世代を確認する（初代 → `dev`、第N世代 → `devN`）
2. 対象の世代ブランチの有無を確認する。第2世代以降が無ければ `release` から `devN` を作成する。初代の `dev` が無ければ `main` から作成する
3. **機能追加かソース修正のどちらかを聞く**
4. どちらか聞いた上で、**ブランチ名を入力してもらう**
5. 入力されたブランチ名にスペルミス・誤字脱字があれば指摘し、修正の有無を確認する
6. 選択に応じて、対象の世代ブランチ（`dev` または `devN`）から派生してブランチを作成する
   - 機能追加 → `feature/[入力したブランチ名]`
   - 修正 → `fix/[入力したブランチ名]`

## コミットフロー

1. 現在ブランチを確認する。`main` または `release` ならコミットしない
2. 作業用ブランチ（`feature/*` または `fix/*`）上であることを確認する。違えばブランチ作成フローへ誘導する
3. コミット前に次を確認する
   - **自分でコミットメッセージを入力したいか**
   - **修正内容に相応しいメッセージを考えてもらいたいか**
4. 前者なら、ユーザーのメッセージを点検する
   - スペルミス・誤字脱字があれば指摘する
   - 差分によりふさわしいメッセージが思いついたら指摘・提案する
   - 指摘した場合は、元のままか修正案かを確認してからコミットする
5. 後者なら差分を見て提案し、承認後にコミットする

## プッシュフロー

1. 現在ブランチを確認する（`feature/*` または `fix/*` を想定）
2. 作業ブランチにプッシュする
3. 作業ブランチにプッシュ後、**作業対象の世代ブランチ（`dev` または `devN`）へリモートマージして問題ないか** を確認する
4. 問題ない場合のみ、確認した方針どおりにマージを進める
5. 問題がある・まだ早い場合は、マージせず作業ブランチの扱いについて次の指示を待つ
6. **リモートの世代ブランチへのマージが完了したら、ローカルもその世代ブランチに切り替える**（例: `git checkout dev2` → `git pull origin dev2`）。作業ブランチに残したままにしない
7. **`release` へのマージはデプロイするときだけ。** 作業ブランチのマージ後に勝手に `release` へ入れない。ユーザーがデプロイ用マージを指示したときだけ、対象世代ブランチを `release` へマージしてプッシュする

## やってはいけないこと

- `main` へのローカルコミット
- `release` への直接コミット、および確認なしの `release` へのマージ／プッシュ
- 確認なしのブランチ作成・コミットメッセージ決定・世代ブランチ（`dev` / `devN`）へのマージ／プッシュ
- スペルミスやよりふさわしいコミットメッセージの指摘をせずに、そのままブランチ作成・コミットを進めること
- `main`・`release`・別世代のブランチから、作業対象でない世代へ `feature/*` / `fix/*` を切ること（必ず作業対象の `dev` または `devN` から）
- リモートの世代ブランチへのマージ完了後に、ローカルをその世代ブランチへ戻さず作業ブランチに居続けること
- ローカルが `dev` / `devN` / `release` の状態で、確認なしにファイル変更を始めること
