# Git Rules

ローカルでの git 操作はこのスキルのルールに従う。ルールを飛ばして実行しない。

## 絶対ルール

- **main ブランチへローカル環境でコミットしない。** 作業前に現在ブランチを確認し、`main` 上ならコミットを拒否して分岐を促す
- **dev は main から派生して作る。** `dev` が無ければ `main` から作成する。作業用ブランチは必ず `dev` から派生する
- **1問ずつ聞く。** まとめて質問しない。選択肢がある確認は選べる形で提示する
- **ローカルが `dev` のまま変更作業を始めない。** ファイル変更がかかる操作を指示されたとき、現在ブランチが `dev` なら、そのまま進めず **作業用ブランチを作り直す（新規作成する）必要があるか** を確認する。必要ならブランチ作成フローへ進む

## ブランチ戦略

```
main
 └── dev
      ├── feature/<ブランチ名>
      └── fix/<ブランチ名>
```

## ブランチ名・コミットメッセージの指摘

ブランチ名やコミットメッセージをユーザーが指定したとき、作成・コミットの実行前に内容を点検する。問題があれば指摘し、修正案を出してから進める（勝手に直して実行しない）。

- **スペルミス・誤字脱字**を見つけたら指摘する（英語の綴り、ローマ字、日本語の誤字、ハイフン位置の明らかな誤りなど）
- **コミットメッセージ**について、差分の内容によりふさわしい表現が思いついたら指摘・提案する（例: 実際は修正なのに「追加」になっている、範囲が広すぎる／狭すぎる、事実とずれる）
- 指摘するときは、問題点・理由・修正案を短く示し、**元の案のまま進めるか／修正案にするか**を確認する
- 問題がなければ指摘せず、そのままフローを進める

## ブランチ作成フロー

1. `dev` の有無を確認する。無ければ `main` から `dev` を作成する
2. **機能追加かソース修正のどちらかを聞く**
3. どちらか聞いた上で、**ブランチ名を入力してもらう**
4. 入力されたブランチ名にスペルミス・誤字脱字があれば指摘し、修正の有無を確認する
5. 選択に応じて `dev` から派生してブランチを作成する
   - 機能追加 → `feature/[入力したブランチ名]`
   - 修正 → `fix/[入力したブランチ名]`

## コミットフロー

1. 現在ブランチを確認する。`main` ならコミットしない
2. 作業用ブランチ（`feature/*` または `fix/*`）上であることを確認する。違えばブランチ作成フローへ誘導する
3. コミット前に次を確認する
   - **自分でコミットメッセージを入力したいか**
   - **修正内容に相応しいメッセージを考えてもらいたいか**
4. 前者なら、ユーザーのメッセージを点検する
   - スペルミス・誤字脱字があれば指摘する
   - 差分によりふさわしいメッセージが思いついたら指摘・提案する
   - 指摘した場合は、元のままか修正案かを確認してからコミットする
5. 後者なら差分を見て提案し、承認後にコミットする

## プッシュフロー

1. 現在ブランチを確認する（`feature/*` または `fix/*` を想定）
2. 作業ブランチにプッシュする
3. 作業ブランチにプッシュ後 **リモートのdev ブランチにマージして問題ないか** を確認する
4. 問題ない場合のみ、確認した方針どおりにマージを進める
5. 問題がある・まだ早い場合は、マージせず作業ブランチの扱いについて次の指示を待つ
6. **リモートの `dev` へのマージが完了したら、ローカルも `dev` に切り替える**（`git checkout dev` → `git pull origin dev`）。作業ブランチに残したままにしない

## やってはいけないこと

- `main` へのローカルコミット
- 確認なしのブランチ作成・コミットメッセージ決定・dev へのマージ／プッシュ
- スペルミスやよりふさわしいコミットメッセージの指摘をせずに、そのままブランチ作成・コミットを進めること
- `main` や `dev` 以外から直接 `feature/*` / `fix/*` を切ること（必ず `dev` から）
- リモート `dev` へのマージ完了後に、ローカルを `dev` へ戻さず作業ブランチに居続けること
- ローカルが `dev` の状態で、確認なしにファイル変更を始めること
